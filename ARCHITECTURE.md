# Архитектура

## Общая схема

```
                     data/*.json            ← источник правды контента
                          │
          tools/build_webapp_data.py        ← генератор (CI проверяет свежесть)
                          │
                          ▼
   ┌──────────────┐   webapp/generated/content_core.js + content_track_*.js
   │ Telegram Bot │            │
   │  (aiogram 3) │            ▼
   │              │   ┌──────────────────────┐
   │  launcher +  │──▶│  Telegram Mini App   │
   │  fallback    │   │  статика, без сборки │
   └──────┬───────┘   └──────────┬───────────┘
          │                      │  localStorage — основное хранилище
          │                      ▼
          │           ┌──────────────────────┐
          └──────────▶│  Sync API (FastAPI)  │  ← необязателен
             общий    │  SQLite + merge      │
             .env     └──────────────────────┘
```

## Принципы

**Приложение работает без сети и без сервера.** Всё состояние живёт в
`localStorage`. Синхронизация — улучшение, а не условие работы: при
недоступном API приложение молча продолжает работать локально. Обучение не
должно останавливаться из-за инфраструктуры.

**Источник правды — читаемые JSON.** Не база, не сгенерированный файл.
Контент правится текстовым редактором, проходит через валидатор и превращается
в один JS-файл для приложения. CI падает, если сгенерированное отстало.

**Тонкий бот.** В чате нельзя нормально показать план, кольцо готовности и
разбор кейса. Попытка сделать это привела бы к дублированию логики в двух
местах, которое неизбежно разъедется. Поэтому бот — launcher, а fallback в чате
даёт только то, что в чате действительно работает.

**Расчёты чистые и воспроизводимые.** `readiness.js` не читает хранилище: всё
приходит аргументами, включая текущее время. Одинаковый вход даёт одинаковый
выход, поэтому расчёт можно проверить в Node без браузера.

**Никаких внешних зависимостей во фронтенде.** Ни сборщика, ни npm, ни CDN.
Единственный внешний скрипт — `telegram-web-app.js`, без него Mini App не
стартует. Это проверяется тестом.

## Слои

### data/ — контент

Семнадцать JSON-файлов, каждый со своей схемой. Связи между ними — по строковым
идентификаторам, целостность проверяет `tools/validate_content.py` (более 6700
проверок).

Тринадцать файлов принадлежат треку профессии, четыре (`english_*.json`) —
сквозные: раздел «Английский для IT» виден на всех треках, а пустой `track_ids`
внутри записи означает «во всех треках».

Правило: контент не знает о коде. В нём нет ни CSS-классов, ни HTML,
ни путей — только данные и ссылки между ними.

### tools/ — обработка контента

| Скрипт | Назначение |
|---|---|
| `content_lib.py` | загрузчик и индексы, общий для всех остальных |
| `validate_content.py` | схемы, уникальность, ссылки, дубли, количества, следы референса |
| `build_webapp_data.py` | генерация `content_core.js` и трековых файлов, режим `--check` для CI |
| `audit_sources.py` | проверка URL по сети и свежести дат |
| `deduplicate_questions.py` | поиск почти-дублей и конфликтующих ответов |
| `generate_content_report.py` | отчёт о покрытии и пробелах |

Генератор детерминирован: сортировка ключей, фиксированные разделители, никакой
даты внутри файла. Без этого проверка свежести в CI давала бы ложные
срабатывания при каждом запуске.

### webapp/ — Mini App

**Модули состояния** (подключаются в этом порядке — проверяется тестом):

| Модуль | Ответственность | Хранилище |
|---|---|---|
| `generated/content_core.js` + `content-loader.js` | контент: общая часть и файл выбранного трека | — |
| `srs.js` | интервальное повторение | `interview_srs_v1` |
| `progress.js` | цель, серия, профиль, история | `interview_progress_v1`, `interview_profile_v1`, `interview_history_v1`, `interview_exam_date_v1` |
| `readiness.js` | расчёт готовности и план к дате | — (чистые функции) |
| `sync.js` | обмен с сервером и правила слияния | `interview_sync_v1` |
| `app.js` | связующий слой для экранов | — |

**Вспомогательные:** `nav.js` (кнопка «назад» Telegram, haptic, тосты),
`icons.js` (встроенные SVG), `search.js` (единый поиск), `heatmap.js`,
`service-worker.js`, `theme.css`.

**Почему есть `app.js`.** Семнадцать страниц не должны каждая по-своему
понимать, что такое «выполненный шаг плана» или «засчитанное действие».
Вся логика состояния живёт в одном месте, страницы занимаются отрисовкой.

**Разделение ключей хранилища** продиктовано слиянием: `progress` и `profile`
меняются с разной частотой и по разным правилам, а история вообще
append-only. Один общий ключ означал бы, что любое изменение конфликтует
со всем остальным.

### api/ — синхронизация

| Модуль | Ответственность |
|---|---|
| `auth.py` | проверка подписи `initData` (HMAC-SHA256), чистые функции |
| `merge.py` | правила слияния, зеркало `webapp/sync.js` |
| `models.py` | валидация входящих данных (Pydantic) |
| `storage.py` | SQLite: схема, транзакции, история |
| `app.py` | маршруты, авторизация, лимиты |

## Ключевые решения

### Почему готовность считается так

Требования задают пять блоков с весами 35/25/20/10/10. Внутри блоков расчёт
устроен так, чтобы процент нельзя было набрать формально:

* **Знания** — 60% от общей освоенности плюс 40% от средней по темам. Среднее
  по темам добавлено намеренно: при усреднении только по вопросам крупная тема
  перевешивает мелкую, и слабое место маскируется. Вопросы взвешены по
  сложности. Просроченные повторения снижают балл на величину до 15%: знание,
  которое уже забывается, не должно считаться свежим.
* **Mock interview** — покрытие категорий, качество и объём. Одна высокая
  самооценка без повторного захода даёт 75% от своего веса: подтверждением
  считается повтор.
* **Кейсы** — доля пройденных, качество и покрытие критических.
* **Словарь** — освоенность по SRS. Термин попадает в SRS только после
  проверки; открытая карточка не даёт ничего.
* **План и регулярность** — 70% выполнение обязательных шагов, 30% доля
  активных дней за две недели. Серия сознательно не берётся главным
  показателем: она отражает дисциплину, а не знания.

**Ограничители** не дают обойти слабые места:

| Условие | Потолок |
|---|---|
| нет ни одной полной сессии mock interview | 74% |
| меньше трёх завершённых кейсов | 79% |
| критическая тема ниже 40% | 69% |
| охвачено меньше 60% обязательных тем | 64% |

Ограничитель показывается как сработавший, только если он реально срезал
набранный балл. Профиль показывает и набранное, и показанное значение.

**Английский в расчёте не участвует.** Готовность отвечает на вопрос «готов ли
я к собеседованию по профессии», а язык — отдельная ось. Смешать их значило бы
выдавать выученные слова за понимание работы, поэтому прогресс английского
живёт в своём разделе профиля и в своих коробках SRS (`ew:`, `ewr:`, `ed:`,
`eph:`), а в дневную цель и серию идёт наравне с остальной учебной работой.

У слова **две коробки, по одной на направление**: `ew:` — узнавание (вижу
`queue`, вспоминаю значение), `ewr:` — производство (знаю смысл, достаю
английское слово). Это разные навыки, и второй, тот самый, что нужен, чтобы
говорить, даётся заметно позже. Общая коробка засчитывала бы лёгкую сторону за
трудную и возвращала слово на повтор не тогда, когда оно забывается. Фразы
тренируются только в сторону производства (`eph:`): ситуация по-русски →
английская фраза.

Письменные задания — единственная часть английского с **объективной** оценкой:
там не самооценка, а проверка текста по чек-листу жанра (`webapp/writing.js`).
Поэтому в профиле хранится не балл, а факт «прошло» и число попыток. Сам текст
письма не сохраняется и не синхронизируется: это черновик человека.

**Самооценка из настройки не участвует в расчёте вообще.** Она нужна для
приоритизации плана. Это проверяется тестом: максимальная самооценка не меняет
процент.

**Незаполненный трек не получает процента.** Показать «12%» по пустому банку
значило бы выдать отсутствие контента за оценку пользователя.

### Почему план к дате считает не только тесты

Наивный расчёт «сколько вопросов осталось / сколько дней» игнорирует, что кейс
занимает существенно больше времени, чем ответ на тест. Поэтому оставшаяся
работа переводится в условные единицы: повтор — 1, вопрос mock — 3, шаг
плана — 4, кейс — 8. Дневная норма считается из суммы.

### Почему правила слияния продублированы

`webapp/sync.js` и `api/merge.py` реализуют одни и те же правила. Дублирование
намеренное: клиент должен уметь сливать состояние офлайн — например, когда
приложение открыто на двух устройствах, а сеть появилась только сейчас.

Цена — риск расхождения, и это самая дорогая поломка синхронизации: прогресс
тихо теряется на одном из устройств. Поэтому есть тест паритета: одни и те же
фикстуры прогоняются через Node и через Python, результаты сравниваются
побайтово (`tests/test_sync.py` + `webapp/_sync_check.mjs --dump`).

Слияние **идемпотентно**: повторный обмен не меняет состояние. Без этого
свойства состояние «дрейфовало» бы при каждой синхронизации.

### Почему read-merge-write в одной транзакции

Два устройства, синхронизирующихся одновременно, читают одно состояние, и
второе затирает первое. `BEGIN IMMEDIATE` берёт write-lock сразу: конкурент
ждёт и читает уже слитое. Покрыто `tests/test_load.py` — 12 параллельных
записей, ни одна не теряется.

### Почему дата собеседования синхронизируется по времени установки

Собеседование переносят и вперёд, и назад, поэтому «более поздняя дата
побеждает» — неверное правило. Побеждает та, которую установили позже; для
этого рядом хранится метка времени.

### Почему service worker network-first для кода

Cache-first быстрее, но после выката пользователь остаётся на старой версии, а
данные при этом уже новые. Расхождение проявляется как необъяснимые ошибки.
Network-first с таймаутом 4 секунды даёт свежий код онлайн и полноценную
работу офлайн.

### Почему в чате нет оценки свободного текста

Оценивать ответ подсчётом совпадений слов — имитация: её легко обмануть
перечислением терминов, а пользователь примет результат за объективный. Честнее
показать разбор, эталон и рубрику, и попросить оценить себя. В готовность идёт
только самооценка, подтверждённая повторным заходом.

## Потоки данных

**Ответ на вопрос теста.**
`quiz.html` → `App.recordQuizAnswers` → `SRS.gradeMany` (коробки) +
`Progress.recordAction` (дневная цель, серия) → `App.recomputeRoadmap`
(пересчёт шагов плана) → `Sync.schedulePush` (отправка через 4 с).

**Расчёт готовности.**
`App.readiness()` собирает срез: контент, карта SRS, профиль, дни активности,
число полных сессий mock → `Readiness.compute` → блоки, ограничители, темы,
пробелы, следующее действие.

**Синхронизация при старте.**
`Sync.boot()` → POST `/api/state` с локальным состоянием → сервер сливает и
возвращает результат → клиент сливает возвращённое со своим текущим (за время
запроса оно могло измениться) → применяет.

## Что намеренно НЕ сделано

* **Нет сборщика фронтенда.** Семнадцать статических страниц не требуют
  инструментов сборки; их отсутствие означает, что проект не сломается от
  устаревших зависимостей через год.
* **Нет фреймворка.** Задача — отрисовать списки и карточки. Виртуальный DOM
  здесь не окупается.
* **Нет внешней базы.** SQLite покрывает нагрузку с большим запасом; PostgreSQL
  добавил бы отдельный сервис без выигрыша.
* **Нет своей авторизации.** Личность даёт Telegram; собственные пароли — это
  ответственность за их хранение без всякой пользы.
* **Нет серверной проверки прогресса.** Сервер доверяет клиенту. Продукт
  помогает готовиться, а не выдаёт сертификат, поэтому защита от накрутки
  своего же процента не окупается.
