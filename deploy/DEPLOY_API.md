# Сервис синхронизации: развёртывание и эксплуатация

API нужен только для того, чтобы прогресс жил на нескольких устройствах.
Mini App полностью работает без него — при недоступном API приложение молча
остаётся на локальном хранилище. Это осознанное решение: синхронизация не
должна быть точкой отказа для обучения.

## Что хранится

| Таблица | Что | Ключ |
|---|---|---|
| `state` | SRS, прогресс, профиль, дата собеседования | `user_id` |
| `attempts` | история попыток (тесты, mock, кейсы, снимки готовности) | `user_id + id` |

`user_id` — идентификатор Telegram, полученный **только** из подписанного
`initData`. Из тела запроса он не берётся никогда.

## Установка

Виртуальное окружение и пользователь общие с ботом — см. [DEPLOY.md](DEPLOY.md).

```bash
sudo -u interview /opt/interview-trainer/.venv/bin/pip install -r api/requirements.txt
sudo cp deploy/interview-trainer-api.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now interview-trainer-api
```

Сервис слушает `127.0.0.1:4200`. Наружу его отдаёт Caddy на пути `/api/*` —
напрямую в интернет он смотреть не должен.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BOT_TOKEN` | — | обязательна: ею проверяется подпись `initData` |
| `DATABASE_PATH` | `api/state.db` | файл базы |
| `API_CORS_ORIGIN` | пусто | нужна, только если Mini App на другом домене |
| `API_RATE_MAX` | 60 | запросов в окне на пользователя, 0 отключает |
| `API_RATE_WINDOW` | 60 | длина окна в секундах |
| `API_INITDATA_MAX_AGE` | 86400 | максимальный возраст `initData`, защита от повтора |
| `LOG_LEVEL` | INFO | уровень логирования |

Токен обязан быть **тем же**, что у бота: подпись `initData` формируется им.
Разные токены дают бесконечные 401, и это самая частая ошибка настройки.

## Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | живость, доступен без авторизации |
| GET | `/api/state` | состояние пользователя |
| POST | `/api/state` | слить присланное с серверным и вернуть результат |
| GET | `/api/attempts` | история попыток |
| POST | `/api/attempts` | слить историю |
| DELETE | `/api/me` | удалить все данные пользователя |
| GET | `/api/stats` | размер базы, только для авторизованных |

Всё, кроме `/api/health`, требует заголовок `X-Init-Data`.

## Почему слияние, а не перезапись

Пользователь занимается с телефона и с ноутбука. Если сервер просто принимал бы
последнее присланное состояние, устройство, не выходившее в сеть день, стирало
бы прогресс другого. Поэтому:

* коробки SRS — побеждает бо́льшая, при равной — более поздний срок повтора;
* дни активности — максимум по каждому дню;
* самооценки mock и кейсов — лучшая оценка, число заходов — максимум;
* статус требования вакансии не откатывается назад;
* история — объединение по `id` без дублей;
* дата собеседования — та, которую установили позже по времени, а не более
  поздняя календарно: собеседование переносят в обе стороны.

Read-merge-write выполняется в транзакции `BEGIN IMMEDIATE`, поэтому два
устройства, синхронизирующихся одновременно, не теряют обновлений. Это
покрыто тестом `tests/test_load.py`.

Правила продублированы в `webapp/sync.js` и `api/merge.py` — клиент должен
уметь сливать состояние офлайн. Расхождение между ними ловит тест паритета
`tests/test_sync.py`: он прогоняет одни и те же фикстуры через обе реализации.
**При правке одного файла обязательно правьте второй.**

## Бэкапы

```bash
sudo -u interview bash deploy/backup_db.sh
```

Скрипт использует `sqlite3 .backup` (простое копирование файла при включённом
WAL даёт несогласованный снимок), затем **проверяет** копию: целостность и
читаемость таблиц. Непроверенный бэкап обнаруживается сломанным ровно тогда,
когда он нужен.

По расписанию:

```bash
sudo crontab -u interview -e
# ежедневно в 4:15
15 4 * * * bash /opt/interview-trainer/deploy/backup_db.sh >> /var/log/interview-backup.log 2>&1
```

Хранится 14 последних копий (`KEEP`). Копии лежат на той же машине — для
защиты от потери диска нужен внешний экземпляр.

### Восстановление

```bash
sudo systemctl stop interview-trainer-api
cd /opt/interview-trainer/api
gunzip -c backups/state-20260727-041501.db.gz > state.db
sudo chown interview:interview state.db
sudo systemctl start interview-trainer-api
curl -s localhost:4200/api/health
```

## Диагностика

| Симптом | Причина и что делать |
|---|---|
| Все запросы 401 | токен API не совпадает с токеном бота |
| `server misconfigured` (500) | `BOT_TOKEN` не попал в окружение: проверьте `EnvironmentFile` |
| 401 у части пользователей | `initData` протух: увеличьте `API_INITDATA_MAX_AGE` или проверьте время на сервере |
| 429 | сработал лимит частоты; при активной отладке поднимите `API_RATE_MAX` |
| 413 | тело больше 512 КБ: обычно означает раздутое состояние, стоит посмотреть на клиента |
| `database is locked` | не должно происходить: `busy_timeout` 3 с и WAL. Если видите — проверьте, не лежит ли база на сетевом диске |
| Прогресс «откатывается» | почти всегда рассинхрон правил слияния: запустите `python tests/test_sync.py` |

## Приватность

* Удаление данных пользователя: `DELETE /api/me` — вызывается из приложения
  при сбросе прогресса. Сброс только на устройстве оставил бы данные на
  сервере, и они вернулись бы при следующей синхронизации.
* `initData` никогда не пишется в лог: в логи попадает только причина отказа.
* Наружу не отдаётся стектрейс — только общее сообщение об ошибке.
* Публичная документация API отключена (`/docs`, `/openapi.json` → 404).
