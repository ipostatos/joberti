# RedCore Junior SEO — спецификация контента

Целевое устройство трека `redcore-junior-seo` под конкретную вакансию
**RedCore Junior SEO Specialist, TAG-2147**.

Документ описывает, каким трек должен стать. Что именно с каждой существующей
записью делать, чтобы к этому прийти, — в [REDCORE_CONTENT_AUDIT.md](REDCORE_CONTENT_AUDIT.md).

---

## 0. Продуктовый принцип

> Качество важнее количества. Контента в треке уже достаточно. Число вопросов
> не увеличивается ради размера базы: слабые записи переписываются, сливаются
> или удаляются. Каждая запись обязана повышать готовность к собеседованию.

> Человек, прошедший трек, должен уметь решить типовую задачу junior SEO **без**
> приложения, а не только узнать правильный вариант внутри приложения.

Отсюда следует цепочка, к которой ведёт весь трек:

```
ПОНЯТЬ → ОБЪЯСНИТЬ → ДИАГНОСТИРОВАТЬ → ПРИМЕНИТЬ ИНСТРУМЕНТ
       → ПРЕДЛОЖИТЬ РЕШЕНИЕ → ПРОВЕРИТЬ РЕЗУЛЬТАТ → РАССКАЗАТЬ ОБ ЭТОМ ПО-АНГЛИЙСКИ
```

Трек учит не «SEO вообще», а ровно то, что junior обязан знать, уметь сделать
руками и объяснить на интервью.

## 1. Иерархия источников

Факт о поиске не пишется по памяти, если существует первоисточник.

| Уровень | Что это | Когда используется |
|---|---|---|
| **Tier 1 — authoritative** | Google Search Central, Search Console Help, Google Analytics Help, web.dev, Schema.org, MDN | Всё про crawling, indexing, canonical, robots, JS SEO, Search Essentials, HTTP, HTML, разметку. **Единственный допустимый источник для утверждений о поведении Google.** |
| **Tier 2 — official tool docs** | Screaming Frog docs и tutorials, Ahrefs Help, Semrush KB | Всё про поведение конкретного инструмента: режимы краула, лимиты, названия отчётов |
| **Tier 3 — trusted education** | Ahrefs Academy, Semrush Academy, LearningSEO.io | Методология и workflow там, где у Google нет своей методички: сбор семантики, конкурентный анализ, аутрич |
| **Tier 4 — community** | Reddit, Stack Overflow, профильные сообщества | Только реальные кейсы, типовые вопросы интервью, рабочие практики и мнения. **Никогда — как источник истины о Google** |

Правила:

* каждый факт привязан к `source_refs`; исключение — поведение на собеседовании,
  коммуникация и схема STAR, где источника быть не может;
* URL в `library.json` обязан совпадать с URL записи в `sources.json`;
* Tier 3–4 не заменяет Tier 1: если у Google есть страница про то же самое,
  ссылка на блог идёт **дополнением**, а не вместо;
* нельзя выдумывать ссылки. Непроверенный URL получает
  `verification_status: "needs_review"`.

**Базовое ядро источников** (этого достаточно на 90% трека):

1. Google Search Central — SEO documentation
2. Google SEO Starter Guide
3. Google crawling & indexing documentation (robots, canonical, HTTP, JS, sitemap)
4. Google Search Essentials + Spam policies
5. Google Search Console Help (Performance, Page indexing, URL Inspection, Removals, Disavow)
6. Google Analytics Help (GA4: sessions, channel groups, events, traffic-source scopes)
7. Screaming Frog Tutorials
8. Ahrefs SEO Course for Beginners / Technical SEO / Keyword Research
9. Semrush Technical SEO Academy

Новый источник добавляется, только если закрывает конкретную дыру.

## 2. Формат учебного модуля

Каждый урок (`lessons.json`) укладывается в **5–12 минут** и разложен по одной
и той же сетке. Существующая схема полей покрывает её почти целиком; недостающее
добавляется полями, а не свободным текстом.

| Блок сетки | Поле в `lessons.json` |
|---|---|
| CONCEPT — что это | `summary` |
| WHY — зачем SEO-специалисту | `why_it_matters` |
| MENTAL MODEL — как это работает | `key_points` (первые пункты) |
| EXAMPLE — конкретный пример | `example` |
| HOW TO CHECK — как проверить руками | `how_to_check` *(новое поле)* |
| TOOL — чем проверить | `tools` *(новое поле, список)* |
| COMMON MISTAKE — ошибка junior | `common_mistakes` |
| INTERVIEW — как спрашивают | `interview_question` |
| GOOD ANSWER — как отвечать | `short_answer` |
| PRACTICE — практическое задание | `practice_task` |
| SOURCE — первоисточник | `source_refs` |

Правила: минимум 3 пункта в `key_points`, 2 в `common_mistakes`,
`short_answer` — связная речь на 30–60 секунд, а не определение из учебника.
Урок дольше 12 минут делится на два.

## 3. Уровни владения темой

Каждая тема покрывается на четырёх уровнях. Уровень записи фиксируется полем
`level` у вопроса и у мок-вопроса.

| Уровень | Что проверяет | Пример (canonical) |
|---|---|---|
| **L1 — KNOW** | узнавание термина | Что делает `rel=canonical`? |
| **L2 — EXPLAIN** | различение соседних понятий | Чем canonical отличается от 301? |
| **L3 — APPLY** | чтение реального артефакта | Вот HTML страницы. Что означает эта строка? |
| **L4 — DIAGNOSE** | вывод из данных | В GSC user-declared `/product`, Google-selected `/category/product`. Что проверяете первым? |

**L4 — целевой уровень трека.** Тема без единого L4-вопроса не считается
закрытой.

### Ключевые смысловые требования по модулям

**01 Search fundamentals.** Ментальная модель
`DISCOVER → CRAWL → RENDER/PROCESS → INDEX → SERVE/RANK` подаётся как
*концептуальная*, а не как гарантированный линейный конвейер для каждого URL.

**02 Search intent.** Не заучивать таксономию. Главное: выдача показывает, какой
тип результата Google считает подходящим.

**03 Keyword research.** Убрать модель «1 страница = 1 ключ». Заменить на
**1 страница ≈ 1 основной интент / кластер тем**; одна страница ранжируется по
множеству запросов.

**04 On-page.** Убрать мифологию: плотность ключей, «ровно один H1 обязателен»,
«description — фактор ранжирования», жёсткие лимиты символов как требование
Google. Учить связке `title → описывает результат`, `заголовки → структура`,
`контент → закрывает интент`, `внутренние ссылки → обнаружение и контекст`,
`анкор → контекст`.

**06 robots.txt.** `robots.txt` управляет обходом и **не гарантирует**
исчезновение из индекса. Повторяется несколькими разными формулировками.

**07 noindex.** `robots.txt` = не обходить, `noindex` = не индексировать; робот
обязан иметь доступ к странице, чтобы увидеть `noindex`. Нельзя утверждать, что
`noindex` — единственный способ убрать URL: есть 404/410, доступ по паролю,
удаление содержимого, инструмент удаления (временный, ~6 месяцев).

**08 Canonicalization.** Canonical — **сигнал, а не команда**. Разбирается пара
user-declared / Google-selected.

**09 Sitemap.** Sitemap помогает обнаружению и **не гарантирует** индексацию.

**10 Indexing diagnostics.** Статусы разбираются буквально:
`Discovered — currently not indexed` = Google знает URL, но **обхода ещё не
было**; `Crawled — currently not indexed` = обход состоялся, URL в индекс не
попал. `Crawled-not-indexed` **не является диагнозом** «тонкий/дублирующийся
контент» — качество, дублирование, канонизация и рендеринг остаются гипотезами,
которые надо проверить.

**11 GSC.** Практический блок: Performance, Page indexing, URL Inspection,
Sitemaps, Core Web Vitals, Links, Manual actions. Рабочий порядок разбора
падения: `дата → сегмент → запрос/страница/страна/устройство → индексация →
технические изменения → выдача и спрос → гипотеза`.

**12 Screaming Frog.** Hands-on. После одного краула человек обязан найти коды
ответа, редиректы, битые ссылки, title, description, H1, canonical, noindex,
robots, глубину клика, внутренние ссылки, дубли, изображения.

**14 Site architecture.** Модель `HOME → CATEGORY → PAGE`, глубина клика,
страницы-сироты, хлебные крошки.

**17 Off-page.** Минимум понятий: backlink, ссылающийся домен, анкор, `nofollow`,
`sponsored`, `ugc`, релевантность, авторитетность, ссылочный спам, ссылочный
разрыв, аутрич, digital PR. Первоисточник границы между оптимизацией и спамом —
Google Search Essentials и Spam policies.

**19 GA4.** Junior SEO не становится инженером аналитики. Нужно: пользователи,
сессии, вовлечённые сессии, события, ключевые события, source/medium/campaign,
страница входа, органический трафик. Понятия Universal Analytics не выдавать за
GA4.

**20 Sheets.** Всё через SEO-задачи: соединение выгрузки краулера с выгрузкой
GSC, поиск страниц с высокими показами и низким CTR. Не абстрактные упражнения.

**21 Content SEO.** Никакой плотности ключей, минимального объёма и «ИИ-текст =
санкция». Ориентир — people-first content и закрытие интента.

**22 Core Web Vitals.** Остаются в программе: что, зачем, чем проверить
(PageSpeed Insights, CrUX, GSC, Lighthouse). **Не** центральный блок и **не**
отсекающее требование вакансии.

**24 Работа с разработчиками.** Схема задачи:
`PROBLEM → EVIDENCE → IMPACT → EXPECTED BEHAVIOR → ACCEPTANCE CRITERIA → VALIDATION`.

**25 SEO audit — capstone.** Не «найди максимум ошибок», а «найди самое важное».
Десять срезов: crawlability, indexability, canonicalization, architecture,
internal links, on-page, content, performance, off-page, analytics. Приоритет
каждой находки = `IMPACT × SCALE × CONFIDENCE`.

**27 iGaming.** Не перегружать. Цель — понимать контекст работодателя: высокая
конкуренция, партнёрские выдачи, несколько рынков, локализация, коммерческий
интент, различия в регулировании, конкуренция за контент и за ссылки,
брендовые и небрендовые запросы. Ответ на «почему iGaming» — профессиональный, а
не изображение страсти к азартным играм.

**28 Bonus.** Только чтобы понимать разработчиков и технические последствия
правок: endpoint, request/response, GET/POST, статус, JSON, аутентификация,
rate limit; SSR/SSG/CSR, metadata, routing, sitemap, robots, canonical,
redirects в Next.js; таблица, строка, колонка, первичный ключ, SELECT/WHERE/JOIN;
production/staging, build, deploy, rollback, переменные окружения, CI/CD.
Это **не** курс программиста и **не** собеседование по DevOps.

## 5. Архитектура вопросов

### Распределение по типам — на каждую тему

| Доля | Тип | `level` |
|---|---|---|
| 20% | Recall — что это | L1 |
| 30% | Understanding — чем отличается от соседнего | L2 |
| 30% | Scenario — дана ситуация, что происходит | L3 |
| 20% | Diagnostic — даны данные, что проверяете первым | L4 |

### Запрет очевидных дистракторов

Плохо — варианты из разных вселенных:

```
Что такое robots.txt?
  A  управление обходом      B  CSS-фреймворк
  C  база данных             D  формат изображения
```

Хорошо — все варианты правдоподобны, различает только понимание:

```
Что делает robots.txt?
  A  Запрещает обход и гарантирует удаление из индекса
  B  Ограничивает доступ краулера, но не гарантирует удаление из индекса
  C  Запрещает ранжирование, но разрешает обход
  D  Равносилен директиве noindex
```

Действующие правила банка сохраняются: ровно четыре варианта, разбор `why` на
каждый, правильный вариант не длиннее остальных, равномерное распределение
индекса правильного ответа, отсутствие противоречащих пар.

### Feynman-задание

Отдельный тип свободного задания: «объясни простыми словами человеку без
SEO-контекста». Оценивается точность, ясность, краткость, наличие примера.
Формат: мок-вопрос с `mode: "feynman"`.

### Ответы на 30 / 60 / 120 секунд

Для ключевых вопросов мок-интервью задаются три глубины ответа:
30 с — короткий ответ; 60 с — ответ и пример; 120 с — ответ, пример и порядок
диагностики. Поле `answer_depths` у мок-вопроса.

## 6. Механика обучения

### Spaced repetition с изменением формы

SRS остаётся. Но повторение не должно быть одной и той же карточкой: с каждым
заходом форма проверки меняется — это varied retrieval, проверка понятия в новом
контексте.

```
День 0   Что такое canonical?
День 2   Canonical или 301 — в чём разница?
День 7   Google выбрал другой canonical. Почему?
День 21  Вот данные из GSC. Диагностируйте.
```

Реализация: у понятия появляется набор `srs_prompts` разных уровней L1–L4,
коробка повторения одна, а показывается тот вариант, до которого человек дорос.

### Interleaving

После первичного изучения темы вопросы не идут блоками по 20 штук на canonical.
Режим повторения перемешивает темы: `canonical → robots → GSC → HTTP → keyword →
Screaming Frog → indexing`. На собеседовании темы тоже не идут учебниковыми
блоками.

### Оценка уверенности

После ответа человек отмечает уверенность: `1 — угадал`, `2 — не уверен`,
`3 — уверен`.

| Ответ | Уверенность | Что делает SRS |
|---|---|---|
| верный | низкая | вернуть раньше обычного |
| неверный | высокая | **высший приоритет**: это заблуждение, а не пробел |

### Тетрадь заблуждений

Автоматический список ошибок в формате «что человек думал → как на самом деле»:

```
✗  robots.txt убирает страницы из индекса
✓  robots.txt управляет обходом; индексация — отдельный механизм
```

Список периодически перепроверяется отдельным режимом.

### Case-first

По мере продвижения порядок меняется с «урок → вопрос» на
`кейс → попытка → неудача → объяснение → повтор`. Человек сначала пытается
диагностировать, и только потом видит разбор.

### Обязательные практические проекты

Четыре проекта, без которых трек не закрыт:

| Проект | Что сдаётся |
|---|---|
| P1 — Crawl | краул реального небольшого сайта, 10 находок, приоритизация, выгрузка |
| P2 — GSC | разбор доступного сайта: запросы, страницы, CTR, позиции, точки роста |
| P3 — Keyword research | 50–100 запросов → интент → кластеры → привязка к URL |
| P4 — Full SEO audit | итоговый документ: краткая сводка, критичное, техническое, контент, перелинковка, off-page, приоритеты, следующие шаги |

Проект подтверждается пользователем как `evidence` (см. §8) — приложение
не выставляет отметку само.

### Daily Mission

Дневная цель формулируется не «40 вопросов», а планом на время:

```
СЕГОДНЯ — 75 минут
15м  Урок: canonical
15м  Тест по теме
20м  Практика: Screaming Frog
10м  Повторение (SRS)
10м  Объяснение по-английски
 5м  Разбор своих ошибок
```

### Цикл освоения блока

```
1 PRETEST → 2 LEARN → 3 ACTIVE RECALL → 4 PRACTICE
          → 5 CASE → 6 EXPLAIN → 7 SRS → 8 MOCK
```

## 7. Mock interview

### Четыре режима

| Режим | Состав |
|---|---|
| **Recruiter** | расскажите о себе, почему SEO, почему RedCore, почему iGaming, почему смена профессии, сильные и слабые стороны, ожидания по деньгам |
| **Junior SEO** | основы, семантика, on-page, GSC, инструменты, off-page, аналитика |
| **Technical SEO** | HTTP, robots, canonical, индексация, JS, архитектура |
| **Final** | смешанный, 40–50 минут, без подсказок |

### Уточняющие вопросы

Мок перестаёт быть цепочкой «вопрос → ответ → следующий вопрос». У вопроса есть
ветка уточнений:

```
Что такое canonical?
   └─ Почему Google может его проигнорировать?
        └─ Как это проверить?
             └─ Каким инструментом?
```

Поле `follow_ups` у мок-вопроса.

### Рубрика свободного ответа

| Балл | Что означает |
|---|---|
| 0 | нет ответа или ответ неверный |
| 1 | понятие узнано |
| 2 | верное базовое объяснение |
| 3 | верно + рабочий порядок действий и инструмент |
| 4 | верно + порядок + приоритизация + проверка результата |

Для junior **3 = готов к собеседованию**, 4 = сильный junior.

## 8. Опыт кандидата: запрет на выдумывание

Правило жёсткое и проверяется автоматически.

> Приложение **никогда** не генерирует кандидату опыт, которого он не указал.

Нельзя: «Год занимаюсь SEO на собственных и клиентских проектах»,
«I have been working with SEO for about a year».

Вместо одного смешанного текста — два разделённых блока:

| Блок | Кто заполняет | Где живёт |
|---|---|---|
| `model_answer_*` — эталон | контент | `mock_questions.json` |
| `MY EVIDENCE` — личное доказательство | пользователь | `localStorage`, синхронизация |

У мок-вопроса появляется `answer_kind`:

* `generic` — эталон можно произнести как есть, он не содержит личных фактов;
* `personal` — эталон **обязан** быть каркасом («опишите по схеме STAR:
  контекст, задача, ваши действия, измеримый результат»), а личный материал
  человек добавляет сам через `personal_evidence_prompt`.

Шаблоны STAR (`stories.json`) остаются пустыми и редактируемыми только
пользователем — это уже проверяется тестом и сохраняется.

### Цепочка доказательства

Для каждого требования вакансии:

```
Требование → Знание → Доказательство → История → Ответ на интервью
```

Пример:

```
HTML/CSS
  Знание:        85%   (считается приложением)
  Доказательство: —    (заполняет пользователь)
  История:        —    (заполняет пользователь)
  Ответ:         70%   (самооценка в mock)
```

Отсутствие доказательства — нормальное состояние, оно помечается как
`KNOWLEDGE ONLY`, а не как ошибка.

## 9. Готовность: два процента

### Knowledge Readiness (существующий расчёт — сохраняется без изменений)

Отвечает на вопрос «знаю ли я предмет». Веса 35/25/20/10/10:
знания и SRS, mock interview, кейсы, словарь, план и регулярность.
Английский в него **не входит**: смешать язык и предметные знания значило бы
выдавать выученные слова за понимание работы.

### Vacancy Readiness (новый расчёт)

Отвечает на вопрос «готов ли я к **этой** вакансии».

| Блок | Вес | Из чего |
|---|---|---|
| Знание предмета | 20 | процент Knowledge Readiness как есть |
| Обязательные требования закрыты | 25 | статус `confirmed`/`partial` у `importance: required` |
| Доказательства | 15 | доля обязательных требований с непустым `evidence` |
| Инструменты | 10 | требования с `competency: "tools"` |
| Английский | 10 | обязательное языковое требование вакансии + практика раздела «Английский» |
| Mock | 10 | покрытие категорий и качество ответов |
| Истории (STAR) | 10 | заполненных историй из пяти |

Знание входит одним блоком, а не подменяет собой расчёт: человек может знать
предмет и не иметь ни одного доказательства — и это ровно тот разрыв, который
должен быть виден. Требования со статусом `not_applicable` из расчёта
исключаются: это осознанное решение человека, и спорить с ним процентом
неправильно.

Показываются оба процента, рядом и раздельно:

```
Knowledge readiness  ████████░░  82%
Vacancy readiness    ██████░░░░  64%
```

### Жёсткие ограничители

| Условие | Потолок | Статус |
|---|---|---|
| хотя бы одно обязательное требование не начато | 80 | внедрено |
| нет ни одной полной сессии mock | 79 | внедрено |
| обязательное требование по английскому не закрыто | 74 | внедрено |
| у большинства обязательных требований нет доказательства | предупреждение, не потолок | внедрено |
| критическая тема ниже 50% | 69 | P1: сейчас порог 40% в Knowledge Readiness |
| нет практики Screaming Frog (проект P1) | 79 | P1: требует сущности проекта |

Английский **не повышает** Knowledge Readiness ни при каких условиях, но
незакрытое обязательное языковое требование **обязано** снижать Vacancy
Readiness.

Существующие ограничители Knowledge Readiness (74 / 79 / 69 / 64) сохраняются
как есть — правка порогов не входит в задачу этой переработки.

## 10. Английский встроен в SEO

Английский перестаёт быть отдельным списком слов и врастает в предметные темы.

* ключевые термины изучаются **сразу двуязычно**: canonical, crawl, index,
  redirect, query, ranking, backlink, referring domain;
* задания формулируются как рабочие: «Explain robots.txt in English»,
  «Explain the difference between crawling and indexing», «Describe how you would
  investigate a traffic drop»;
* тексты не заучиваются. Используется каркас:

```
ANSWER → REASON → EXAMPLE → CHECK
```

Пример:

> First, I would check whether the drop affects the entire website or a specific
> section. Then I would segment Search Console data by page, query, device and
> country…

Так получается рабочий SEO-английский, а не школьный словарь.

## 11. Свежесть контента

Факты стареют неравномерно, поэтому дата сверки хранится рядом с контентом.

```json
{
  "source_type": "primary",
  "content_reviewed_at": "2026-08-17",
  "volatility": "high"
}
```

| Волатильность | Что относится | Периодичность сверки |
|---|---|---|
| **high** | GA4, интерфейс и статусы GSC, поведение и лимиты инструментов, данные вакансии | каждые 60–90 дней |
| **medium** | поведение поиска Google, Core Web Vitals, JS SEO | раз в полгода |
| **low** | HTTP, HTML, JSON, базовые понятия | по мере необходимости |

Минимальная реализация, не ломающая существующую схему:

* `volatility` объявляется **на теме** (`topics.json`) — устаревает предметная
  область, а не отдельная формулировка. Отсутствие поля означает `low`;
* `content_reviewed_at` хранится **на записи** и обязателен для записей,
  относящихся к теме с `volatility: "high"`, и для вакансии;
* валидатор проверяет формат даты и то, что она не в будущем; просроченная
  сверка — предупреждение и строка в отчёте о контенте, а не падение CI.

Аннотировать всё подряд запрещено: поле без реального смысла превращается в шум.

## 12. Правила для генерации контента

**НЕЛЬЗЯ:**

* выдумывать правила SEO;
* использовать правила плотности ключевых слов;
* выдавать корреляцию за причинно-следственную связь;
* выдавать отраслевые конвенции за требования Google;
* выдумывать опыт кандидата;
* выдавать понятия Universal Analytics за GA4;
* называть canonical директивой;
* утверждать, что `robots.txt` гарантирует удаление из индекса;
* утверждать, что sitemap гарантирует индексацию;
* утверждать, что SSR гарантирует индексацию;
* ставить диагноз по одному статусу `Crawled — currently not indexed`;
* подавать лимиты символов как жёсткие требования Google;
* делать очевидные дистракторы в тестах;
* наращивать количество вопросов ради количества.

## 15. Инженерные ограничения

Переработка не имеет права ломать существующую архитектуру.

* источник правды — `data/*.json`; `tools/build_webapp_data.py` собирает
  `webapp/generated/*`; CI падает, если сгенерированное отстало;
* UI в этой переработке не перерисовывается — меняются данные, расчёты и точечно
  разметка там, где без неё новое значение негде показать;
* никаких секретов, `.env`, файлов БД и пользовательских данных в репозитории;
* новое поле схемы сопровождается проверкой в `tools/validate_content.py` и
  тестом;
* правило письменной проверки продублировано в `webapp/writing.js` и
  `tools/content_lib.py` — новое поле задания добавляется в обе реализации;
* полный прогон перед коммитом: `bash run_all_checks.sh`.
